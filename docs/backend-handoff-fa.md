# راهنمای تحویل هشتیوا به تیم توسعه

## ماهیت تحویل

این کد، نمونهٔ رابط کاربری فارسی و راست‌به‌چپ است. فایل ZIP اولیهٔ Hashtiva شامل بک‌اند .NET، پنل Next.js و پورتال SvelteKit بود؛ خروجی فعلی یک فرانت‌اند استاتیک جداگانه است. بنابراین صرفاً با تنظیم آدرس API به پنل اصلی تبدیل نمی‌شود.

پیشنهاد پیاده‌سازی: این خروجی را به عنوان مرجع UI/UX استفاده کنید و اجزا و مسیرها را در `Hashtiva.Panel.Next` پیاده کنید. پیش از تغییر، README و AGENTS پروژهٔ اصلی را بخوانید. فایل‌های بک‌اند، تنظیمات استقرار و اسرار موجود در ZIP اولیه جزو این تحویل نیستند و نباید همراه نمونهٔ UI منتشر شوند.

## فایل‌ها و ترتیب اجرا

- `dist/index.html`: پوسته و ترتیب بارگذاری.
- `dist/app.js`: داده‌های پایه، helperها و event handlerهای اولیه.
- `dist/upgrade.js`: شبکه‌ها، دستیار نمایشی و بخش‌های توسعه‌یافته.
- `dist/workspace.js`: میز کار، گفتگو، منابع دانش، جریان‌ها، سفارش و محصول.
- `dist/product.js`: ویرایشگر سه‌مرحله‌ای، بازبینی، پرونده مخاطب، شروع کار، گزارش و نقش‌ها.
- CSSها نیز به همین ترتیب روی هم اعمال می‌شوند.

لایه‌های فعلی shared global state دارند و بعضی تابع‌ها را جایگزین می‌کنند. در تبدیل به محصول، اجزا و state را به ماژول‌های مستقل انتقال دهید؛ event handlerهای چندلایه و capture مربوط به composer را بدون بررسی حذف یا جابه‌جا نکنید.

## نقشه اتصال بخش‌ها

نام کنترلرهای زیر از نسخهٔ ZIP بررسی شده آمده است؛ وجود کنترلر به معنی پشتیبانی از تمام قراردادهای UI نیست. قرارداد نهایی باید از Swagger/DTOهای نسخهٔ جاری استخراج شود.

| بخش UI | نقطه شروع بررسی در بک‌اند موجود | کار مورد نیاز |
|---|---|---|
| حساب‌ها | SocialAccountManagerController، InstagramCallBackController، FacebookConnectController | هویت حساب، مجوز اتصال، خطا و وضعیت معتبر؛ بررسی جداگانه پشتیبانی تلگرام/واتس‌اپ |
| محتوا و تقویم | InstagramPostsController | پیش‌نویس پایدار، رسانه، مقصدها، زمان‌بندی، خطای انتشار و وضعیت job |
| صندوق گفتگو | InboxController، InstagramDirectMessagesController، InstagramCommentsController | pagination، تاریخچه، پاسخ، مالک گفتگو، یادداشت داخلی و برچسب |
| محصولات و سفارش | ProductController، OrderController | شناسه پایدار، قیمت عددی، موجودی، مجوز تغییر وضعیت و تاریخچه |
| هویت برند | BrandProfileController | لحن، مخاطب و منابع مورد استفاده توسط دستیار |
| گزارش | InstagramInsightsController | بازه زمانی، منبع شاخص‌ها و تعریف دقیق نسبت‌ها |
| تیم | AccountMembersController | نقش‌های واقعی و enforce شدن دسترسی در سرور |

پایگاه دانش، بازبینی چندمرحله‌ای، ارجاع گفتگو و audit ممکن است به توسعه قرارداد و مدل داده نیاز داشته باشند. مسیر API یا قابلیت تأییدنشده را از روی نام‌ها فرض نکنید.

## وضعیت محلی و جایگزینی آن

stateهای `posts`، `accounts`، `messagesState`، `knowledge`، `flows`، `products` و `orders` و کلیدهای localStorage دادهٔ واقعی نیستند. کلیدهای مهم:

- `ht-posts`: محتوا، متن هر شبکه، تصویر data URL، موعد و workflow.
- `ht-inbox-v3`: گفتگو، پاسخ، یادداشت، برچسب و مسئول.
- `ht-knowledge`، `ht-flows`: منابع و جریان‌های نمونه.
- `ht-accounts`، `ht-channel-state`: حساب و وضعیت شبیه‌سازی.
- `ht-members`، `ht-role`، `ht-audit`: نقش و تاریخچهٔ محلی.
- `ht-products`، `ht-orders`: محصولات و سفارش‌های نمونه.

داده‌های نمونه را به production مهاجرت ندهید. در نسخه واقعی، owner/tenant/account scope، شناسه پایدار، pagination، خطا، loading و invalidation لازم است. تغییر قیمت‌های رشته‌ای فارسی به مقدار عددی و واحد پول روشن ضروری است.

## گردش محتوا

`draft → review → approved / scheduled`

- نویسنده می‌تواند پیش‌نویس بسازد و درخواست بازبینی ثبت کند.
- مدیر/بازبین می‌تواند تأیید کند. این محدودیت در نمونه فقط سمت مرورگر است.
- ذخیره تغییرات باید نسخه محتوا و اعتبار تأیید قبلی را مشخص کند.
- API باید نقش، اعتبار رسانه، حساب مقصد، زمان آینده و idempotency را بررسی کند.
- زمان محلی انتخابی باید همراه timezone به قرارداد زمانی مشخص، ترجیحاً UTC در سرور، تبدیل شود.
- زمان‌بندی واقعی باید با job پایدار سرور اجرا شود؛ تایمر مرورگر قابل اتکا نیست.
- آپلود به storage واقعی منتقل شود؛ نوع/اندازه/ابعاد ویدیو و تصویر بر اساس هر شبکه اعتبارسنجی گردد.
- پیش‌نمایش‌های شبکه تقریبی‌اند و محدودیت رسمی هر سرویس باید جداگانه اعمال شود.

## دستیار

پاسخ فعلی آماده و rule-based است؛ هیچ مدل زنده‌ای متصل نیست. قابلیت‌های قابل مشاهده: پیشنهاد پاسخ، پیشنهاد محتوا، تبدیل سؤال مشتری یا منبع دانش به پیش‌نویس.

برای اتصال واقعی، درخواست از backend عبور کند؛ کلید مدل در مرورگر قرار نگیرد. منابع و مجوز خواندن داده برای هر workspace محدود شود. پاسخ پیشنهادی از اقدام نهایی جدا بماند، ارجاع به انسان و تأیید پیش از ارسال حفظ شود. هزینه، timeout، retry و trace قابل بررسی باشند. نام «AI» به تنهایی نشان‌دهنده اجرای واقعی در نسخه حاضر نیست.

## ترتیب پیشنهادی اجرا

1. تبدیل shell و اجزای ثابت به کامپوننت‌های پنل و اتصال احراز هویت.
2. اتصال حساب‌ها و داده‌های read-only، همراه حالت‌های خالی/خطا/loading.
3. اتصال composer و storage؛ سپس بازبینی و زمان‌بندی سروری.
4. اتصال inbox و مجوز ثبت پاسخ/یادداشت/ارجاع.
5. اتصال منابع دانش و پیشنهادهای AI با بازبینی انسانی.
6. اتصال گزارش، تیم، audit و سفارش‌ها.

## معیارهای پذیرش

- دادهٔ دو workspace یا دو حساب با هم مخلوط نشود.
- نویسنده با درخواست مستقیم API هم نتواند تأیید یا انتشار انجام دهد.
- درخواست تکراری باعث انتشار یا پاسخ تکراری نشود.
- قطع اتصال، timeout، پاسخ نامعتبر و محدودیت نرخ قابل بازیابی باشند.
- تبدیل زمان و نمایش تاریخ شمسی روی timezoneهای مختلف درست باشد.
- بارگذاری رسانه، ذخیره پیش‌نویس، متن مخصوص هر شبکه و بازبینی روی موبایل بررسی شوند.
- ترتیب focus، استفاده با صفحه‌کلید و dialogها با مرورگر واقعی آزمایش شوند.

## محدودیت بررسی

بررسی syntax و آزمون‌های مستقل با DOM stub انجام شده است؛ این بررسی‌ها جایگزین تست مرورگر، E2E، امنیت یا اتصال واقعی API نیستند. بررسی بصری مرورگر در محیط ساخت در دسترس نبود.
